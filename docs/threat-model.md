# Threat model

This is the application-level threat model for the current fictional/Sandbox product. Tests and hosted evidence support specific controls; they do not replace independent security assessment or operational readiness.

| Threat                                            | Boundary/control                                                                                                                                                   | Remaining limitation                                                                                                |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| Client assigns roles or financial state           | Approved memberships, RLS/column grants and service-only protected RPCs                                                                                            | Service credentials have broad authority; restrict and rotate operational access                                    |
| Cross-user or cross-workspace access              | Participant RLS, verified server identity, active demo ticket/workspace checks and actor-specific RPCs                                                             | Continue adversarial testing as new roles/routes are added; expired evidence requires authorized administration     |
| Forged, duplicate or misassociated payment        | Signature verification, canonical completed merchant capture, amount/currency/custom ID checks, durable attempt/evidence guards and idempotent ledger confirmation | Provider delays/review remain external; new genuine tests require explicit authorization                            |
| Simulation represented as captured payment        | Immutable source marker, separate simulated ledger kind, empty PayPal IDs, private-workspace scope and genuine-path rejection                                      | Keep screenshots, narration and exported evidence labeled; simulation is not provider proof                         |
| Public GPS or home address exposure               | Trigger-coarsened public coordinates, separate private relations, expiring visibility and assigned-runner access                                                   | Authorized participants can retain what they saw; privacy policy and retention operations are still needed          |
| Unsafe state transition or duplicate rewards      | Actor-specific locked database state machine, assigned-runner checks and completion guards                                                                         | Matching is approximate and cannot establish road feasibility or real delivery quality                              |
| Prompt injection or invented catalog facts        | Validated read/quote tool registry, catalog-selected IDs and protected writes outside model authority                                                              | Relevance can still be manipulated; users review recommendations and quotes                                         |
| XSS, injection or mass assignment                 | React escaping, strict bounded schemas, parameterized queries and column grants                                                                                    | Production CSP permits inline hydration scripts; nonce-based hardening remains future work                          |
| CSRF                                              | Exact configured Origin for cookie-authenticated writes; independent provider/worker signatures                                                                    | Same-origin compromise is outside this control; canonical domain/redirect configuration matters                     |
| Abuse or resource exhaustion                      | Shared database entry/action limits, bounded request/raster sizes, timeouts and bounded admin/job batches                                                          | Load/edge protection and capacity/queue monitoring need operational validation                                      |
| Unsafe uploads or private consent leakage         | Raster decoding/metadata stripping, ownership checks, server-only bucket writes, short-lived authorized document URLs and immutable originals                      | Local reduced stack lacks Storage; hosted probes do not prove every future file or application workflow             |
| Duplicate email or false delivery claim           | Serialized queue leases, stable provider idempotency key, receipt checks and signature-verified delivery events                                                    | Provider deduplication expires; uncertain old attempts require operator review and inbox delivery is separate proof |
| Data loss, excessive retention or unsafe rollback | Additive migrations, immutable evidence, preserved financial history and restricted deletion requests                                                              | Restore drills and documented retention/deletion execution remain operational work                                  |

No permanent exact-location tracking product is implemented. Availability/trips expire and operational address access is state-limited. Expiry does not automatically purge records. Define retention for trip/rate-limit/demo operational data and addresses while preserving legally appropriate consent, financial and audit evidence. Keep backup/restore and incident ownership separate from a successful demo release.
